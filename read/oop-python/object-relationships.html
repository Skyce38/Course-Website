Reference และความสัมพันธ์ระหว่าง Object

Week5: object references, Association/Aggregation/Composition และ encapsulation ตัวอย่าง Team/Player และ House/Room จาก source โค้ดผู้เขียนลดเหลือส่วนที่ใช้แสดง ownership และ identity ไม่ใช่ fullClinic/Librarylab

เป้าหมายการเรียนรู้

  • แยก is-a จาก has-a และการใช้งาน object ชั่วคราว
  • ติดตาม reference/sharedstate และผลของการ copycontainer
  • เลือก ownership/multiplicity ให้เข้ากับ domain และอธิบาย Pythonlifetime อย่างถูกต้อง

ทำไมไม่ยัดทุกอย่างใน Class เดียว

Week5 pp.3–18 ยก order/address/item และการเก็บ object ไว้เป็น attribute แยกข้อมูลกับพฤติกรรมตามขอบเขตที่เปลี่ยนจริง เช่นอ้าง Addressobject แทนขนานหลาย lists ซึ่ง index คลาดกันได้ Attribute เก็บ reference ไม่ใช่สำเนา object ใหม่ Noneอาจแทนความสัมพันธ์ที่ยังไม่มี;ต้องตรวจ None ก่อนเรียก method

Trace Identity และ Container Copy

เริ่ม p(goals0)→เพิ่มเข้า A ยัง objectp เดิม→p.score ทำ goals1ซึ่ง A เห็นด้วย→remove ออก A→เพิ่มเข้า B ยัง is p และ goals1 ไม่มีการสร้าง Player ใหม่ระหว่างย้าย การทำ Player(p.name)แทนจะเริ่ม goals0และทำประวัติหาย

House สร้าง3rooms พื้นที่20,12,6ตาม sourcepp.37–38 รวม38 การสร้าง room สี่เหลี่ยม?source ไม่ได้ให้รูปทรง จึงไม่แต่ง width/height เพื่อคำนวณพื้นที่ใหม่ total_areaรวมข้อมูล area ที่มีอยู่

team.playersเป็น tuple ใหม่ที่ป้องกัน append ลง container ภายในโดยตรง แต่สมาชิกยังเป็น reference เดิม การเรียก team.players[0].score()ยังแก้ Player ได้ Copycontainer ไม่ใช่ deepcopy;ถ้าต้องการ immutableview ต้องออกแบบให้คืนข้อมูลค่าเช่น room_summaries

Composition ไม่ใช่ Garbage-Collection Command

pp.39–41เน้นว่าไม่มี externalreference ใน interface ตัวอย่างจึงหมดการเข้าถึง room เมื่อ house หมดไป แต่ Python ไม่ห้ามสร้าง Room ลอยๆหรือเก็บ alias ถ้าโค้ดเปิดทาง del houseลบ reference หนึ่งชื่อ ไม่รับรอง part ถูกทำลายทันทีเมื่อยังมี alias อยู่ แยกความเป็นเจ้าของเชิง domain ออกจากการจัดสรร/เก็บกวาดหน่วยความจำ และอย่าใช้ private เป็นเหตุผลว่าบังคับ ownership ได้100%

ต้นทุนและการประยุกต์

Team การตรวจซ้ำ/ลบด้วย list ต้อง O(n),สร้าง tuplesnapshotO(n);การเข้าถึง object ที่รู้อยู่แล้ว O(1)ภายใต้แบบจำลองนี้ House.total_area เป็น O(r)สำหรับ r ห้อง ไม่ใช่ O(1)เพียงเพราะเป็น property LabLibrary/Gym/Clinic มีหลายความสัมพันธ์พร้อมกัน:หนังสือ/สมาชิกอาจ aggregate แต่ record ที่ระบบสร้างมี composition ตามโจทย์ ต้องดูสัญญาแต่ละ task ไม่ใช้คำว่า has-a แล้วตัดสินทั้งหมด

ในห้าสถานการณ์ source pp.51–55: Playlist/Song เป็น aggregation; Invoice/InvoiceLine, Car/Engine และ University/Department เป็น composition ตามเงื่อนไขการสร้าง/ไม่ย้าย/ยุบตามเจ้าของที่โจทย์ระบุ; Doctor/Patient เป็น association เมื่อใช้ผ่าน examine โดยไม่เก็บ reference เป็น attribute การสรุปนี้อาศัยเงื่อนไขโจทย์ ไม่ใช่ชื่อ nouns เพียงอย่างเดียว

ข้อผิดพลาดที่พบบ่อย

คืน list ภายในให้ caller ลบทิ้งได้;สร้าง part ใหม่แทนเก็บ reference เดิม;สืบทอด Customer จาก Account เพียงเพราะมี account;คิด tuple ทำให้ทุก object ข้างใน immutable;ถือ del เป็นคำสั่งทำลาย graph ทุกตัว
