## Ownership and reproducibility

All drawings are original programmatic illustrations, not copies of lecturer slides or third-party pictures. Editable SVGs live in `docs/diagrams/iot-final/`; only lossless WebP images under the local course image directory load in readers. No SVG embedding, renderer rewrite, framework, website JavaScript, new font binary, external image hotlink or runtime dependency is introduced.

Author with `python scripts/iot-visual-build.py`; rasterize with `node scripts/iot-visual-raster.cjs`; integrate additively with `node scripts/iot-visual-markdown.cjs`; then `node scripts/build.cjs`. Authoring uses an existing desktop Chrome/Playwright installation (`PLAYWRIGHT_MODULE`) and existing Python/Pillow (`STUDY_PYTHON`). SVGs specify an installed Thai-capable font, tested with Windows Leelawadee UI; other systems need a suitable installed Thai font. Identical raster bytes are verified in the same Chrome/font/toolchain environment, not promised across different font engines. No software/font installation is performed by the scripts.

The lesson renderer already supports local raster images, captions, attribution and alt text. It remains unchanged. The builder adds only one conditional, versioned IoT stylesheet for the new diagrams. Its scoped width/aspect-ratio rules reserve space before lazy loading, preserve the selected theme around fixed neutral teaching images and constrain print size. Image colors are not inverted in Dark mode because signal/power/ground meanings must remain stable.

## Technical and source review

Source IDs/physical-page conventions are defined in [the original-source ledger](iot-final-source-coverage.md). All seven original files remain locally available/read-only; the Phase13 content audit is reused where unchanged. This review compared diagram labels to current lesson paragraphs/sketches, original Week9 formula/circuit evidence, Week12 PIR/relay/OLED evidence and book module/GPIO distinctions. Original pages and private student/source documents are not published.

- **01–03:** classic ESP32-WROOM is the selected example. No physical header positions or universal ESP32-family pinout are claimed. Board/module/SoC are distinct. The four-layer Device/Network/Platform/Application drawing is an authored explanatory model requested for this phase, not an assertion that the book uses exactly that layer taxonomy or that cloud services are installed.
- **04–06:** conceptual signal plots are not measurements. Module VCC/GND/AO/DO labels are functions, not connector order. GPIO34 is input-only/no internal pull resistors on the selected classic chip. ADC12 has4096 codes/max4095; raw is not calibrated voltage or moisture percentage.
- **07–09:** Trigger≥10µs and Echo500µs use deliberately different schematic scales; no internal sensor latency is invented.343m/s=0.0343cm/µs, round-trip17.15cm and one-way8.575cm match the lesson. Some module documentation instead uses340m/s; the diagram never silently swaps conventions.
- **10–12:** water pins32/33/25/26/27 match the authored sketch. Echo must traverse a level interface, never directly enter GPIO. At the explicit nominal5.0V input,10k/15k gives3.0V. ESP32 Series datasheet5.3, physicalp.52/Table5-3 lists VIH≥0.75×VDD and≤VDD+0.3 at3.3V/25°C; nominal3.0V fits2.475..3.6V. This does NOT verify module VOH/VOL, resistor tolerances, pulse loading/rise time, board supply, or real wiring. Check these and TRIG VIH before use. Each LED has its own330Ω resistor and labelled A/K return. Source sample distances are not thresholds;30/50cm boundaries remain explicitly authored. H100cm is the existing worked-example datum, not a measured tank size.
- **13–16:** setup executes once per boot/reset; the loop arrow returns to loop, never setup. The condition diagram branches true/false and rejoins; it does not execute both outputs. GPIO configuration/read/write and the five interface types are separate comparisons, not a serial chain. Example input/LED semantics remain unchanged.
- **17–18:** SDA21/SCL22, UART RX16/TX17 and SPI18/19/23/27 match the existing code. I2C requires appropriate pull-ups;0x3C is an assumed address, not a scan result. Other-device address is unspecified, distinct and conceptual. Crossings without dots are not junctions. UART routes TX→RX; SPI MISO points toward the controller. All illustrated logic must be compatible; VCC is checked per actual module.
- **19–20:** PIR receives changing IR; shaded zones are reception fields, not transmitted ultrasound. Waveforms are illustrative module output, not actual movement times/counts. Actual hold, retrigger, warm-up and polarity remain device-specific.
- **21–25:** GPIO controls a compatible driver/module IN, never a bare coil. Contact circuit is a safe low-voltage LED example, with COM/NO shown de-energized/open. Control ground and load return are labelled separately; optocouplers do not establish isolation by themselves. RelayactiveLOW/PIRactiveHIGH and OLED128×64/0x3C remain authored assumptions. The integrated controller branches into parallel relay and OLED paths, not relay→OLED in series. Timer diagrams count from last observed HIGH:1000→11000 without retrigger; HIGH9000 moves the deadline to19000. LOW11000 may correctly display No Motion/Lamp ON. Mock OLED panels are text explanations, not literal pixel/font dimensions or hardware screenshots.

Five corresponding connection tables appear immediately below the wiring figures (10,17,18,21,24), separately from the diagram geometry. They distinguish Signal, Power, Ground, UART, I2C and load roles. Hardware assumptions are recorded individually in the JSON inventory and reiterated in captions/nearby prose. No mains/breadboard or direct GPIO→coil wiring is recommended.
